# Requirements (traceability source)

Distilled from the interface.ai take-home brief *"Assignment A — Computer-Use Automation System"*. Every
spec cites the IDs it satisfies. `/trace-requirements` builds the coverage matrix from these IDs. Keep the
IDs stable: to add a requirement, append a new ID and never renumber.

**Evaluation order (brief §7):** system design → correctness of the core loop → robustness & error handling
→ human-in-the-loop → generalization → safety & data handling → code quality → communication.
**Not rewarded:** feature breadth, framework name-dropping, scaling infrastructure (queues, clusters,
multi-tenant plumbing).

## Core (must-have, brief §3)

| ID     | Requirement                                                                                                                                                                                                                                               | Done when                                                                                       |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| R1.1   | Accept a **goal** (natural language) + a **target** (app/URL/entry point) as input.                                                                                                                                                                      | The CLI `discover` takes both.                                                                   |
| R1.2   | An LLM-driven **observe → decide → act** loop runs against a live surface until the goal is met or a stop condition is hit (max steps, timeout, dead end).                                                                                                 | All stop conditions are implemented and tested with a scripted fake model.                       |
| R1.3   | Actually interacts with a real UI (click, type, navigate, read state). **Bias toward mechanisms that work without a clean DOM.**                                                                                                                         | The accessibility tree is the primary perception; a real run exists in `evidence/`.             |
| R2.1   | After a successful run, emit a **typed, serializable artifact** decoupled from the model transcript.                                                                                                                                                     | The artifact compiler emits JSON that validates against the schema.                              |
| R2.2   | The artifact expresses **ordered steps/actions**.                                                                                                                                                                                                        | Schema + fixture.                                                                                |
| R2.3   | The artifact expresses **how each target is identified**, with robustness reasoning.                                                                                                                                                                    | A locator ladder per target, with a rationale in the schema docs/ADR.                            |
| R2.4   | **Typed input parameters** (supplied per invocation).                                                                                                                                                                                                    | A params schema, validated before replay.                                                        |
| R2.5   | **Typed outputs / extraction** and their shape.                                                                                                                                                                                                          | An outputs schema, validated after replay.                                                       |
| R2.6   | A **checkpoint / success condition**.                                                                                                                                                                                                                    | Per-step checkpoints + a final success condition.                                                |
| R2.7   | **Versioned and reviewable** by a human reviewer *and* a calling agent (what it does, needs, returns).                                                                                                                                                   | semver + content hash + human-readable summary + JSON Schema.                                    |
| R3.1   | Replay a saved artifact with input params **without the LLM in the decision loop**.                                                                                                                                                                     | `replay-engine` has no dependency on `agent`; a test proves it.                                  |
| R3.2   | **Stable targeting**, **checkpoint verification**, and the declared outputs returned to the caller.                                                                                                                                                     | Functional tests against `mock-bank`.                                                            |
| R3.3   | Detect runtime conditions — validation error, record not found, permission denial, unexpected dialog, session timeout, slow/failed load, app error — and respond deliberately.                                                                           | One `define-runtime-condition` per condition, each with an injected-fault test.                  |
| R3.4   | The result contract distinguishes **business outcome** vs **recoverable condition** vs **hard failure**.                                                                                                                                                | A discriminated union; recoverables are handled inside the run and logged.                       |
| R3.5   | A structured result: success (outputs) · known business outcome · failure (**which step, expected, observed**).                                                                                                                                         | Result schema + evidence refs on failure.                                                        |
| R4.1   | An explicit, **configurable allowlist** (domains/routes, action types). The agent must not act outside it.                                                                                                                                              | `policy` config + enforcement tests on the agent, replay, and human paths.                       |
| R4.2   | Distinguish **safe/reversible** from **risky/irreversible** actions and handle the risky class conservatively (justify the choice).                                                                                                                     | Risk class per action type + the conservative behaviour + an ADR.                                |
| R4.3   | **Never persist** secrets/credentials/tokens/full PII in artifacts or logs. Redact.                                                                                                                                                                     | A redaction layer at every sink + the `/safety-review` scan passes on `evidence/`.               |
| R5.1   | A **structured log** of what the agent did **and why**.                                                                                                                                                                                                  | JSONL run log with the reasoning summary per step.                                               |
| R5.2   | At least one **richer signal on failure** (screenshot / DOM or a11y snapshot / trace).                                                                                                                                                                  | Screenshot + a11y snapshot (+ Playwright trace) attached to the failure result.                  |
| R6.1   | **Detect and route**: identify a stuck/blocked state and raise an **intervention request** with context (capability/goal, current step, state/screenshot, why).                                                                                        | An intervention-request schema + triggers from the agent, replay, and risky-action paths.        |
| R6.2   | **Take control of the live session**: a human operates the *same* session (not a fresh one), then hands control back; context/evidence preserved; **the human's actions are recorded**.                                                               | The same browser context; the recorder captures human actions as steps.                          |
| R6.3   | **Pause / cede / resume** on the same session, with an explicit model of **who is (or should be) in control**.                                                                                                                                          | A control-lease state machine + tests.                                                           |
| R6.4   | A minimal (mockable) operator surface: pause, expose the session, signal resume, capture actions — **plus a clear design for the full version**.                                                                                                        | `apps/operator` + a REPORT §5 design.                                                            |
| R7.1   | *(design)* **Surface abstraction**: how the schema and engine extend to legacy web and desktop; the seam between perceive/act and the recorded flow.                                                                                                    | The `Surface` port + REPORT §4 + an ADR.                                                         |
| R7.2   | *(design)* **Multi-tenant reuse**: share or specialize artifacts across tenants running the same vendor app; detect and manage per-tenant/version drift.                                                                                                | The schema leaves room for base + overrides + REPORT §4 (optionally S5).                         |
| R-REAL | **The discovery run must be real**: at least one genuine LLM-driven run against a live surface, with evidence in `/evidence/`.                                                                                                                         | `/capture-evidence` output is committed.                                                         |

## Deliverables (brief §6 — exact paths and headings)

| ID  | Deliverable                                                                                                                                                                                                                                                                                                       |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | `/README.md`: setup and run (keys/config, how to run without live services) + the **demo path**: the exact commands to run the agent on a goal, then replay the resulting artifact.                                                                                                                                  |
| D2  | `/REPORT.md` (~1–3 pages) with exactly these headings: **1. Architecture · 2. Artifact schema · 3. Determinism & error handling · 4. Heterogeneity & multi-tenant · 5. Escalation & handoff · 6. Safety · 7. Cuts**.                                                                                               |
| D3  | `/evidence/`: a saved example artifact + logs from a **discovery run** and a **replay run**; ideally **one replay that hits an error/exceptional state** (bad input, not found, injected failure). A screen recording is optional.                                                                                |
| D4  | A public GitHub repo; the URL on its own line, emailed to assignments@interface.ai from the address used to apply. No zip. Secrets stay out of the repo.                                                                                                                                                           |

## Stretch (brief §8 — pick at most 1–2, only on a solid core)

| ID  | Stretch goal                                                                                                  |
| --- | ------------------------------------------------------------------------------------------------------------- |
| S1  | Agent-facing capability catalog (discover + invoke by name with typed args, shown being invoked).              |
| S2  | Code generation from an artifact (page object / test file).                                                    |
| S3  | Confidence & approval: reliability score; gate unattended replay on `draft → approved`.                        |
| S4  | Assisted fallback: a bounded, policy-checked, single-step LLM recovery on replay failure, recorded as evidence. |
| S5  | Canonicalization / cross-tenant reuse: parameterized routes; a base artifact applied to a variant with overrides. |
| S6  | Multi-run stability: replay N times and report flakiness.                                                      |
